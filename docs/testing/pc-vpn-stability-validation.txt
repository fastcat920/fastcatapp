PC 连接稳定性优化与实机验收流程
日期：2026-11-08

交付范围
代码已分批修改、自检，尚未打包安装 PC 客户端，也未操作实机系统代理、DNS 或 TUN 做联网验证。
必须使用重新构建的客户端和本次 Go 核心一起测试；不能只替换界面文件后继续使用旧核心。
Windows/Linux 已交叉编译 amd64 核心，macOS 已编译 arm64 核心；这些是核心编译验证，不是完整桌面安装包编译或运行验证。
未推送 GitHub，未覆盖其他既有工作区改动。

第一批：启动、停止与异常退出
- 桌面 TUN 创建结果参与启动确认，失败返回明确错误；连接中重新应用 TUN 配置失败，也会清除连接状态并清理。
- 核心通信意外断开时，清除连接计时和运行状态，恢复本应用设置的代理/DNS，清理旧核心；不会无限自动拉起或反复触发授权。用户可重新连接。
- 主动断开/重启不被当作异常退出；启动等待、配置超时处理继续保留。
- 桌面运行刷新任务带连接代次，停止期间尚未结束的旧任务不能恢复旧定时器或写回旧状态。
- 自检额外发现并修复：legacy HTTP/SOCKS/TUN 不属于自定义入站表；桌面停止时显式关闭它们。离线应用配置时不安装 TUN，保留用户的 TUN 选择用于下次连接。

第二批：系统代理
- 已启用系统代理时，连接流程等待写入及回读验证，再发布已连接；失败进入回退。
- 主动断开先恢复系统代理，再关闭底层监听。
- 连接中系统代理开启/更新失败，如果没有正常启用的 TUN 提供路由，也会退出连接状态；TUN 模式保留可工作的隧道并提示代理问题。
- 插件原有串行队列和代理配置所有权保护继续使用，避免覆盖其他应用后来修改的代理/PAC。

第三批：退出、重启与 macOS DNS
- 取消700ms后强行继续重启，以及清理未完成时无条件退出；先完成网络设置恢复、核心关闭，再销毁服务并退出/重启。失败保留应用并提示。
- 重启启动器失败时尝试重新取得单实例锁。
- macOS DNS 按原网络服务分别保存和恢复，支持带空格的服务名称；不把 Wi-Fi 原 DNS 写入网线服务。
- 自动 DNS 的启用与恢复串行；保留用户/其他软件在之后做出的 DNS 修改；命令失败、无法回读不算成功。

自动自检
- Flutter/Dart 针对性回归59项通过，包括真实本地IPC断开、正常关闭不误报、刷新任务停止、系统代理确认/回退、慢清理、DNS跨服务恢复和外部修改保护。
- 修改范围 Dart 静态分析通过，无问题。
- Go 主模块与 listener 包测试通过；新增真实本地 TCP/UDP 端口释放、离线配置不安装 TUN、TUN 构建失败不发布就绪且可重试的测试。
- Windows amd64、Linux amd64、macOS arm64 Go 核心编译通过。
- 差异空白检查通过。
这些结果不代表系统代理权限、TUN驱动/网卡、睡眠唤醒或外网流量已在桌面真机通过。

实机测试准备
每个平台分别进行，不将一个平台通过算作其他平台通过。使用测试账号、原有有效订阅与同一网络。
记录：系统版本、客户端构建、核心版本/摘要、网络类型、代理模式、节点名称，以及测试前系统代理/PAC与DNS状态。
报告不公开密码、订阅、Token、完整出口IP或企业内部代理地址。地区核验只记录 loc= 值。
保存首次失败的时间、客户端日志和系统状态；后续恢复另记，不能用多次重试覆盖首次失败。缺少权限受限环境或第二种网络时，对应项记为受阻。

1. 系统代理模式基础流量（Windows/macOS/Linux）
操作：关闭TUN、开启系统代理，选香港/日本等已知节点，点击一次连接。查看系统HTTP/HTTPS代理，再用浏览器打开 https://www.cloudflare.com/cdn-cgi/trace 。
预期：系统代理指向客户端本地端口，界面才显示已连接；网页成功，loc与节点实际出口一致。节点名称不等于地区证明。
证据：客户端状态、系统代理状态、浏览器loc、启动日志。
随后主动断开：代理恢复原状态，本地代理监听不再接受新连接，网页不因残留本地代理而失去网络。

2. 系统代理设置失败/拒绝授权
操作：在已有权限受限的测试环境验证；macOS若出现客户端相关授权提示，测试取消。也检查连接中切换系统代理开关。
预期：没有TUN兜底时，写入/回读失败不会持续显示已连接；出现失败提示并回退。系统代理原值保留。已成功工作的TUN不因单独系统代理失败被误判为失效。
限制：不要为了本项擅自更改企业策略或破坏系统配置。无法产生此条件就记受阻，不能判通过。

3. TUN启动及权限拒绝（支持TUN的桌面环境）
操作：先关闭系统代理以免掩盖TUN问题，在客户端启用TUN并允许所需授权，连接后用不读取系统HTTP代理的应用访问trace。
预期：系统TUN网卡/路由存在，实际流量通过。不能只凭本地端口或节点测速成功判定。
再验证拒绝/取消授权：应明确回退或失败，不得声称TUN已经生效。连接中更改TUN参数失败时也不得保留假连接。
正常断开后检查TUN网卡/路由已清理；无需重开应用即可正常上网。

4. 核心意外退出
操作：保持连接，在系统任务管理工具中仅结束FastCat代理核心进程一次，保留主应用；不要结束无关程序。Helper模式也需单独验证。
预期：主应用及时离开已连接状态，计时停止；系统代理恢复或明确显示恢复失败，TUN不继续伪装工作；无无限重启、无反复授权。
记录失败到状态变化的耗时。之后只点击一次重新连接，验证实际流量恢复。

5. 连续连接、断开和重连
操作：等每次完成后再切换，连续5轮；另验证处理中重复点击会被正确拦截。每轮检查网页及系统状态。
预期：一次操作只对应一套核心/监听；断开后端口和路由释放，不出现上次任务覆盖新连接、重复定时器或永久转圈。

6. 退出与清缓存重启
操作：分别在已连接、未连接状态从托盘退出；另测试清缓存并重启。先保存工作。
预期：代理/DNS恢复后再关闭核心；重启仅出现一个新实例。新实例可正常连接。
若清理授权等待或失败：不应700ms后绕过清理强退；应保留应用和失败提示。处理权限问题后可再次操作。
注意：普通关闭窗口与托盘退出分别验证，前者按产品约定进入后台，不能混作退出测试。

7. macOS DNS恢复（macOS专项）
操作：记录Wi-Fi与网线各自原DNS，启用客户端自动设置DNS功能并连接；切换到另一网络，再断开/退出。
预期：原服务恢复其原DNS，各服务没有互相覆盖。另测试原本自动DNS，以及网络服务名包含空格的情况。
附加对照：测试期间在系统设置主动修改DNS，再让客户端恢复；后改的值应保留，不能被客户端旧快照覆盖。测试后自行恢复所记录的原值。

8. 睡眠、唤醒与网络恢复
操作：保持连接，系统睡眠约1分钟后唤醒，刷新trace；关闭Wi-Fi约10秒再恢复原Wi-Fi；条件允许时再切换Wi-Fi与网线。
预期：真实流量和连接状态一致，不出现长时间假连接、持续离线提示或授权循环。需要手动重连、仅浏览器旧连接异常等情况均单独记录。
本轮代码检查不保证所有系统的电源/网络驱动行为，必须实测。

# N1 第三阶段：发送布局与完整结束流程

日期：2026-11-24，Asia/Shanghai。

## 结果

合并布局通过本轮功能及记录数量验收，已于17:19将独立实验入口 zlhk.fastcat.ink:18461 切换为coalesced。18463临时对照入口已停止。正式443、CatNode 93/94未改动；没有更新安卓正式App、面板或订阅。

这仍是TCP实验原型，不是生产发布，也没有证明GFW识别率下降。

## 改了什么

- 认证成功响应保持立即发送。直接等目标载荷再发200，会让等待Dial/CONNECT的应用与等待应用请求的目标互相等待，因此没有采用这种合并。
- 将HTTP chunk长度、记录正文和chunk尾部放到一次TLS明文Write；FIN与HTTP终止chunk同批输出。没有增加定时等待，没有修改密钥交换、认证、加密、填充范围或业务内容。
- 接管连接后复制已缓冲数据，使用独立Reader和标准chunk解码器，不再读取原Request.Body。
- CloseWrite等待整个外层HTTP请求写完；服务端消费外层结束标记后，再有界完成TLS关闭流程。正常结束的关闭阶段预算为5秒且不超过会话期限；取消未完成业务仍直接中断。
- 重复读取FIN保持EOF；写入FIN后禁止继续写业务数据，重复FIN不再次发送。

## 最终交错对照

同一荣耀TFY-AN00、Wi-Fi、服务器、证书、目标源和32KiB内容。每轮交换先后顺序，10轮，每条业务均新建TCP/TLS连接。

| 指标 | 旧布局 | 合并布局 |
|---|---:|---:|
| 完整事务成功 | 10/10 | 10/10 |
| 服务端加密TLS记录中位数 | 19 | 15 |
| 服务端去重TCP载荷中位数 | 38340.5 B | 38251 B |
| 服务端RST包 | 0 | 0 |
| 客户端RST包 | 0 | 0 |
| 首响应头P50 / P95 | 875.7 / 4689.6 ms | 952.8 / 2165.7 ms |
| 完整事务P50 / P95 | 1064.1 / 5334.0 ms | 1105.9 / 4771.6 ms |

“完整事务”本轮增加了载荷校验、N1 FIN、外层HTTP EOF与TLS终止读EOF检查；不能直接与前两阶段仅完整HTTP响应的耗时比较。Go TLS可能在记录边界接受没有close_notify的底层EOF，故字段名为tls_shutdown_eof_observed，不单靠该EOF宣称验证了收到对端通知；实现双方均调用CloseWrite发送TLS关闭通知。

抓包两组各10条流，TCP重组连续、TLS无未解析尾部，未将缺包或不完整流当成记录减少。加密记录包括握手、业务和结束阶段，不等于TCP包数。

记录中位数减少4条，约21%；总TCP载荷仅相差约90字节，且受随机填充、签名长度等影响，不能说省流21%。首响应头P50反而略高；10个样本的P95是最大值，网络长尾明显，本轮不主张速度提升。

## 未通过的中间版本

1. 首轮旧布局10/10，新布局4/10；新布局10条抓包流均出现服务端RST，部分成功请求的RST发生在载荷交付后。所有失败数据保留在initial-failed-round，没有只挑成功样本。
2. 初始关闭实现把N1 FIN误当作整个HTTP请求完成，可能在外层结束字节仍在途时关闭socket。新增故意延迟外层结束标记的回归，旧逻辑稳定失败，输出保留在negative-outer-eof-regression.txt。
3. 等待外层结束后，一轮HTTP载荷检查两组均10/10，但仍有尾部RST，不能作为干净关闭验收。该轮保留在fixed-http-body-round；其中旧布局抓包只有9个ClientHello，也未用它作最终记录数量结论。
4. 安卓又暴露Hijack后继续使用原请求体的错误；HTTP服务恢复了panic，早先测试进程仍打印PASS。这不算合格结果，stdout和说明保留在android-pre-detach-*。改为独立读取，并加强fixture后重新验证。
5. 最终同时验证N1、HTTP与TLS结束流程，双方完成有界关闭后再关闭socket，重新取得两组完整抓包和0 RST结果。

run_phase3_ab.py现在检查服务实际布局。入口已更新后直接运行会拒绝发送请求，防止把两条合并布局误标成A/B。重新比较需先明确恢复18461 legacy及18463 coalesced的隔离条件。

## 结论边界与下一步

本轮证明减少了可解释的额外独立写入，并补齐关闭正确性；没有证明更难被分类。ClientHello、SNI、独立端口和TLS实现特征没有因此隐藏。普通流式HTTPS在第二阶段约17条记录的结果来自另一轮，不能将19→15解释成已匹配所有网站。

下一步应在不同载荷大小、交互节奏和持续流量下，与匹配的普通流式HTTPS做独立留出样本对照，判断变化是否具有稳定价值；之后再考虑发送调度和吞吐。UDP、复用、完整App、动态账号、面板计量、多网络长期识别与耗电均未完成；第一阶段88.7秒下载长尾也没有在本轮宣称修复。

# N1 第五阶段：客户端 FIN 合并与新样本验收

日期：2026-11-24。安卓：荣耀 TFY-AN00；当前 Wi-Fi → zlhk.fastcat.ink:18461/TCP → 回环合成源。原生实验程序，不是正式 App/VPN。

## 结果

已定位并实现客户端发送优化。旧客户端用独立的 TLS Write 发送 HTTP 终止 chunk（5 字节 `0\r\n\r\n`），此前一条 Write 已发送 N1 FIN。新实现将两者放在同一 Write，保持全部标记和校验，不引入等待。

本地观察：请求头、单个业务记录、FIN、HTTP 结束标记原为 4 次明文 Write，合并后为 3 次。公网新样本证实客户端加密 TLS 记录总数 **6 → 5**，流式 RPC 也是 5。加密 type=23 记录总数可能包含加密握手和关闭消息，不等于业务消息数量；大载荷也不能假设每次 Write 永远只有一个 TLS 记录。

72/72 请求完整成功，三组各 24 条，全部载荷逐字节正确、结束检查通过，抓包未观察到任何一组的客户端或服务端 RST。消除了一处固定分段差异，但**没有通过“不可区分”或抗 GFW 验收**：加入字节数后，本批合成样本仍可被简单规则区分。

## 实现与安全边界

- 私有客户端配置新增 `client_emission: coalesced`，省略仍使用 legacy；未知值拨号前拒绝。服务端不需要升级，旧/新客户端与 legacy/coalesced 两种服务端布局的四种组合均通过本地往返测试。
- 请求头由 Go 标准库生成并验证，只保留已完成的头部序列化结果，立即发送；真实业务记录随后增量发送。
- 每次 Write 立即发送，无定时聚合、不等待更多业务或 FIN。共用已有 chunkBatchWriter 将完整 HTTP chunk 与 N1 记录成批写入，FIN 同时携带外层终止块。
- 保留显式 FIN、单向半关闭、接收 FIN 后稳定 EOF、禁止 FIN 后写入、外层 HTTP EOF、有界 TLS 关闭流程；未减少证书检查、未关闭加密、未更换密钥交换/填充、未增加重放。
- 新路径不再为每条连接创建 io.Pipe 和请求发送协程；这是实现结构变化，尚未量化 CPU、内存或耗电收益。
- 本地观察只保存写入长度和帧类别，不记录目标、Cookie、业务内容或密钥。

测试覆盖交互单字节即时返回、约 500 KiB 双向数据、服务端先发/空响应、下行 FIN 后继续上行、重复 FIN/EOF、错误认证、取消释放和延迟外层结束。Mac `go test -race -count=1 ./...`、`go vet ./...` 与安卓 ClientEmission/Coalesced 测试通过。保留原先会把 HTTP 后台 panic 判为失败的夹具。

## 独立采样方案

方案在采集前写入 PHASE5-PLAN.md。训练载荷 1536/12288/98304 B，未见尺寸验证 3072/24576/196608 B，未复用第四阶段已看的留出尺寸。突发每块 16 KiB；分段推送每块 8 KiB、间隔 15 ms；短于一块的样本没有实际间隔。每个单元两次重复，旧/新客户端与 RPC 各 24 条，总 72 条。训练与留出各 36 条，内部随机交错，新建 TCP/TLS 连接；本轮无失败和补单。

服务端保持第四阶段二进制，SHA256 为 `0e5ed17e6e94ac775d8d52b0a65f26e5db57fd2c1efd57ab0144d7b8707c2d8e`；仅临时开启同一个有界 RPC 对照接口。客户端新二进制分别用 legacy/coalesced 配置，同一源代码与 TLS 栈，减少版本差异。

## 本轮耗时

| 方式 | 完整成功 | 首个业务字节 P50 / P95，ms | 全事务 P50 / P95，ms |
| --- | ---: | ---: | ---: |
| N1 旧客户端 | 24/24 | 2308.9 / 8324.3 | 2720.5 / 10029.3 |
| N1 合并客户端 | 24/24 | 2040.9 / 7465.4 | 3109.4 / 8666.2 |
| 合成流式 RPC | 24/24 | 1620.1 / 5589.1 | 2586.6 / 9598.0 |

P95 使用 nearest rank。数据合并了六种尺寸和两种节奏，包含 DNS/TCP/TLS、授权、目标请求与结束处理，不是 RTT 或纯下载吞吐。RPC 提前确认头不当成业务首包。

合并版首包 P50/P95 和全事务 P95 较低，但全事务 P50 较高，**不能认为整体速度更快**。每个单元仅两次，网络波动明显，未作统计显著性结论；此次优化主要针对 FIN 收尾多余分段，并不会按机制自动缩短此前已收到的首包时间。不能与第四阶段不同时段数据直接推断性能进步。

## 留出判别结果

两套预定特征：计数（双向加密记录总数、小于等于 256 B 的记录数）；完整特征另加双向唯一 TCP 载荷字节数的对数。单层阈值规则仅用训练批次选取，留出后不改阈值。

TP/TN/FP/FN 分别为正确命中 N1、正确排除 RPC、误报 RPC、漏报 N1；每组留出为 12 条 N1 + 12 条 RPC。

| 对照 | 训练选择的规则 | 留出 TP/TN/FP/FN | 平衡准确率 |
| --- | --- | --- | ---: |
| 旧客户端：仅计数 | client_records > 5.5000 | 12/12/0/0 | 100.0% |
| 合并客户端：仅计数 | server_small_records < 6.5000 | 8/8/4/4 | 66.7% |
| 合并客户端：计数 + 字节数 | log_client_tcp_bytes > 7.6057 | 12/12/0/0 | 100.0% |

旧客户端加入全部特征后仍选客户端记录数，留出 100%。合并后客户端记录总数与 RPC 相同，计数规则转而使用服务端小记录数，留出降为 66.7%，存在 4 次误报和 4 次漏报；不能把这个数值当成真实检测器的上限。完整特征则用客户端字节量继续分开本批样本，留出 100%。

三组客户端唯一 TCP 载荷字节中位数：旧 N1 2085 B，新 N1 2064 B，RPC 1971 B。随机填充导致各次不同，21 B 的中位差不等于每次节约量，不能宣称节省 1/6 总流量。N1 的认证请求后还承载目标 HTTP 请求和 FIN；RPC 使用短 JSON 上传，两者上行语义、长度及交互阶段并不完全匹配。字节量可区分该合成实验，不证明它是可泛化的代理特征，也不能据此盲目补齐到某个固定字节数。

本批 ClientHello 归一化特征一致，但都是同一 Go TLS 栈，并非真实浏览器。样本单设备、单网络、有限尺寸，不包含真实网页群体、游戏、UDP、多路复用、长期负载或真实 GFW 标注。所有百分比均为这个实验中的规则分数，**不是实际 GFW 识别率或封锁概率**。

## 抓包与恢复

72 个握手与样本按顺序匹配，均见 SYN，双向 TCP 重组连续、双向 TLS 尾部无未解析数据，抓包内核丢包统计为 0，三组 RST 均为 0。

原始 pcap 为 7113759 B，SHA256 `081645731185a694bf3b24e805f40889cb2e52b50f11782cc66469bb55d71fdb`，完整文件保存在服务器 `/opt/fastcat-n1-lab/phase5.pcap`，权限 600。因原 SSH 连接取回原始文件缓慢，停止了非必需下载，本地残片明确命名为 `.partial`，未用于分析。已通过独立 SSH 会话在服务器直接运行同一分析器，取回完整且通过校验的匿名元数据；未解密会话或导出 TLS 密钥。

临时 RPC 接口已关闭并返回 404；恢复后旧/新客户端各一次校验成功，正式 HTTPS 返回 200，catnode-native-93/94 仍 active。已删除安卓临时测试可执行文件，未安装 APK、未更新面板、未改正式节点、未推送 GitHub。新路径保留为实验显式配置，没有悄悄切换原有默认。

## 后续建议

保留本次合并实现。下一步先构造上行载荷长度和交互阶段匹配的正常流式业务对照，检查服务端小记录的来源，再用新留出样本验证；暂不继续合并必须即时发送的确认头，也不去掉 FIN 或 TLS 关闭检查。当前证据不支持为了让一个合成分类器得分降低而添加大量随机填充。

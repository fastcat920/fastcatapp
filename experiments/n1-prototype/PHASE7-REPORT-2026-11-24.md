# N1 第七阶段：完整写入限额优化与安卓公网 A/B

日期：2026-11-24。设备为当前连接的荣耀 TFY-AN00，安卓独立原生程序，经同一 Wi-Fi 访问 zlhk.fastcat.ink 的隔离测试入口。未安装或更新正式快猫 APK，不是 App/VPN 验收。

## 结果

限制下行完整业务写入大小的实验已实现并通过自检。主实验 32/32 成功、无 RST：当前布局产生 131 条由大写入拆分出的短尾，限额布局为 0；自然小 DATA 为 7 → 8，没有明显转化成更多自然小记录。这个具体成因得到改善。

主实验服务端加密 TLS 记录总数 **1025 → 886，减少约 13.6%**；服务端唯一 TCP 载荷 **4999484 → 4996133 B，只减少约 0.067%**。记录减少不等于同幅度节约流量，也不等于 IP 包数减少，更不能推导 GFW 识别概率。

耗时没有一致改善。因基线两次 1 MiB 突发速率波动大，又补测四对请求：限额 4/4 成功，基线 3/4 成功、最后一条 30 秒超时。全部尝试合计限额 20/20、基线 19/20；样本少且环境波动，**不能据此宣称限额方案速度或稳定性更好**。暂保留实验开关，不切换正式默认。

## 改动

- 服务端实验选项 `-data-write-limit 16384`，仅支持与 `-emission coalesced` 一起使用，默认 0 保持原实现。
- 从目标读取下行 DATA 时将载荷限制为 16337 B：16384 − N1 头 8 B − 最大填充 31 B − HTTP chunk 边界 8 B。编码后再次检查完整 Write 大小，不超过 16384 B，否则报错，不能截断数据。
- 只改变下行记录的发送尺寸；接收端仍支持原 16384 B 载荷，客户端上行未改。序号、随机填充、FIN、HTTP EOF 和 TLS 关闭校验全部保留。
- 小数据立即转发，没有延时拼包、额外填充、自动重放或目标内容删除。TLS 自适应记录大小仍可把较小写入拆开，本参数不是所有场景都无小记录的保证，也不限制 TLS 自身的握手消息。

本地测试穷举 0–31 B 填充，检查最坏情况下完整写入大小；验证超限写入未输出任何字节，并核对大数据转发、交互单字节、半关闭、FIN、拒绝认证和取消释放。Mac race 测试和 vet、安卓对应回环测试通过。

## 主实验方案

采集前固定 PHASE7-PLAN.md。基线 18461、限额 18463：相同服务器二进制、TLS 配置/证书、目标源和安卓合并客户端。每对内随机先后，整个请求对顺序打乱，随机种子 20261127。

输出大小 5003/33331/131101/1048576 B，使用新非整块尺寸与 1 MiB 大数据。分别突发 16 KiB 源写入和分段 4 KiB/8 ms 源写入，每个单元两次，每组 16 条，总 32 条。验证载荷及完整结束，并将服务端明文写入事件与 TLS 记录逐项对齐。试跑不计入正式样本。

这是实现 A/B，不拟合识别模型，也没有用本轮结果选择识别阈值。不同端口及网络噪声仍是局限；未进行显著性检验、长期运行、锁屏或耗电测试。

## 写入与记录核对

| 主实验指标，每组 16 条 | 基线 | 限额 |
| --- | ---: | ---: |
| 超过 16384 B 的业务写入 | 153 | 0 |
| 大写入拆出的短小加密记录 | 131 | 0 |
| 自然小 DATA 记录 | 7 | 8 |
| 所有小加密记录，含握手/响应头/FIN/关闭 | 234 | 104 |
| 服务端加密 TLS 记录总数 | 1025 | 886 |
| 服务端唯一 TCP 载荷，B | 4999484 | 4996133 |
| TCP RST | 0 | 0 |

“小记录”为加密 TLS 记录长度 <=256 B。原布局最大明文业务写入 16431 B；限额布局最大 16384 B。限额样本中未观察到早期自适应 TLS 产生的小拆分尾，但这不是协议保证。自然短 DATA、确认响应头、FIN、TLS 握手与关闭记录仍然存在，不应为了消除它们而破坏交互或完整性。

32 个 ClientHello 与样本顺序对应，双向 TCP 连续重组、TLS 无未解析尾部；事件对齐均成功。同一 pcap 中分别解析两个端口，再按时间合并，保留原始各单位日志和源 ID；归一化 ID 只用于连接元数据关联。

## 耗时与 1 MiB 读取速率

| 主实验方式 | 完整成功 | 首个业务字节 P50 / P95，ms | 全事务 P50 / P95，ms |
| --- | ---: | ---: | ---: |
| 当前合并布局 | 16/16 | 1413.2 / 3629.2 | 3065.1 / 18555.1 |
| 16 KiB 写入限额 | 16/16 | 2234.6 / 7701.9 | 3136.5 / 7825.1 |

P95 使用 nearest rank。主实验限额版首包 P50/P95 较高，全事务 P95 较低，但中位数略高；不能概括为全面提速。限额主要处理下行 DATA 分段，没有修改 DNS/TCP/TLS 建立过程。各单元仅两次，网络时序仍可能显著影响结果。

`payload_read_mbps` 是目标 HTTP 响应头之后的正文读取和校验速率，包含等待、已缓冲数据及校验，不是纯线路速率；成功载荷才有效。全事务还包含入口准备、目标请求和关闭，不能混用。

主实验 1 MiB 样本（Mbps）：

| 发送节奏 / 重复 | 基线正文读取 | 限额正文读取 |
| --- | ---: | ---: |
| burst / 1 | 0.50 | 5.89 |
| burst / 2 | 9.83 | 5.60 |
| paced / 1 | 2.98 | 3.90 |
| paced / 2 | 2.06 | 4.53 |

基线两次突发分别约 0.50 与 9.83 Mbps，因此没有仅凭两次计算性能结论。

## 追加四对复测：保留失败

看到主实验异常后，预先写入 bulk-declaration.json，随机交换先后，补四对 1 MiB 突发请求。它是后续诊断样本，不是独立留出验证。为不再改动已恢复的主服务，使用两个临时入口：18463 为基线、18465 为限额；同一新二进制，参数相同。它与主实验时间、端口不同，分别报告。

| 补测轮次 | 基线正文读取 Mbps | 限额正文读取 Mbps |
| --- | ---: | ---: |
| 1 | 5.39 | 1.32 |
| 2 | 6.91 | 7.49 |
| 3 | 1.43 | 7.10 |
| 4 | **30 秒超时，失败** | 7.57 |

两者都出现了慢样本。成功的七条完整流中，基线 3 条出现 170 条拆分短尾，限额 4 条为 0；分母不同，仅说明成功样本中的机制复现，不把这七条当成全部成功率。

最后一条基线在 30 秒总预算内未完成：约 10.66 秒收到第一业务字节，随后正文读取直到截止时间。服务端抓包唯一 TCP 载荷约 280836 B，仍处在正文传输阶段，客户端尚未发送 FIN；失败流有 3 个 RST 包和不完整 TLS 尾部。服务端记录 1 次 transport error，未见 panic。它没有完成 1 MiB，不能套用完整响应的记录归因，也不能误判为已完成数据后的 FIN 收尾失败。传输为何如此慢尚未进一步定位，不能直接归咎于网络或某个流控策略。

失败数据和 stderr 均原样保留，没有补单替换。原测量代码在失败时仍按请求大小计算了 payload_read_mbps，该字段无效，未进入吞吐表；已修正为只在完整载荷校验成功时输出，并加入坏载荷回归测试。原测量版本源码快照与最初哈希匹配，最终修正版与实验产物的哈希分开保留。

## 建议

保留限额实验选项：它在本轮有效消除了超出 16 KiB 的小拆分尾，实际字节开销下降很小。先不要据此宣称更隐蔽、更快或大规模更稳定，也不切换正式默认。恢复检查仍有 TLS 超时，因此整体性能和稳定性验收未通过。下一步若推进性能，应优先定位慢样本的 TCP/TLS 建立和正文传输阶段，并扩大同轮、同尺寸的吞吐样本；不靠延长超时或隐藏失败让成功率变好。

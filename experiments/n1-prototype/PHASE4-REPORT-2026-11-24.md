# N1 第四阶段：多尺寸与流式对照验收

日期：2026-11-24。设备：荣耀 TFY-AN00，安卓原生独立程序；当前 Wi-Fi → zlhk.fastcat.ink:18461/TCP → 本机合成源。未安装或更新正式 App，不是 VPN/App 验收。

## 结论

第二轮 72/72 请求的逐字节载荷及消息结束检查通过，N1 与 RPC 均未观察到 TCP RST。但 N1 仍有稳定可区分的客户端记录数量：本批样本 N1 为 6、GET 为 3、RPC 为 5。引入流式 RPC 后，“像流式网站”本身不足以消除这一实现特征。本阶段没有修改 N1 线格式或发送策略，也没有证明其隐蔽性提升。

这些数值是 TLS 外层 type=23 加密记录总数，包括可能的加密握手/关闭消息，不能当成 6 条业务消息。未解密记录，不能仅凭计数断定多出的记录就是 FIN；需要下一轮带发送事件标记的隔离测试定位。

## 测试与优化内容

- 新增三组共用的数据源、512 B 至 128 KiB 六种尺寸、突发与 4 KiB/30 ms 分段推送。小于一块的样本没有实际间隔，不是完整聊天/游戏交互模型。
- 使用首个业务字节计时，避免把 RPC 提前确认头误当业务首包。逐字节流式校验，检测少收、多收和内容错误。
- 修正测试客户端过早关闭目标 HTTP 发送方向的问题：提前半关闭会取消 Go HTTP 合成源的上下文，导致慢速推送被截断。现先读完整响应再发 N1 FIN；未改变协议半关闭语义。
- 对照 RPC 明确消费上传 EOF，再发送业务流，避免处理器结束阶段的并发读取；测试夹具会将后台恢复的 panic 判为失败。
- 可变公共资源与 RPC 有尺寸、请求体和等待上限，仅临时启用；采集后已关闭。
- Mac race 测试及 vet 通过，安卓 Workload 回环测试通过。保留本地已修复问题和部署前错误试跑说明，不混入公网结果。

## 第二轮时间统计

| 方式 | 完整成功 | 首个业务字节 P50 / P95，ms | 全事务 P50 / P95，ms |
| --- | ---: | ---: | ---: |
| N1 | 24/24 | 1254.1 / 3864.3 | 1680.3 / 4755.0 |
| HTTPS GET | 24/24 | 950.7 / 2356.5 | 1290.4 / 3101.7 |
| 流式 RPC | 24/24 | 1573.8 / 2637.8 | 2061.3 / 3718.1 |

每组 24 条，均为新连接，包含 DNS/TCP/TLS 与请求处理；不是节点 RTT，也不是暖连接复用。业务阶段预算 30 秒；普通诊断拨号/握手辅助函数另有 15 秒预算，服务端握手/头部上限 10 秒。失败阶段预算并非完全对称，后续应统一细分阶段计时。统计合并六种尺寸及两种节奏，只有两次重复/单元，P95 使用 nearest rank。该表用于描述本轮，不用于宣称协议速度排名；普通 GET 少一次隧道认证/目标请求交互，完整耗时还包含不同的关闭路径。报告不包含大文件、长期负载、并发或锁屏能耗验收。

## 预先声明的判别实验

训练尺寸 512/8192/65536 B，留出尺寸 1024/16384/131072 B；训练与留出各 36 条。训练阶段选择单阈值规则，只用 TLS 记录数、小记录数和 TCP 唯一载荷字节数等六个预定特征，不使用 IP、端口、时间戳、真实载荷大小或标签作为输入。两批内部随机顺序，留出后不调整规则。

| 训练对照 | 训练选中规则 | 留出 TP / TN / FP / FN | 留出平衡准确率 |
| --- | --- | --- | ---: |
| 仅 GET | 客户端加密记录数 > 4.5 | 12 / 12 / 12 / 0 | 75% |
| GET + RPC | 客户端加密记录数 > 5.5 | 12 / 24 / 0 / 0 | 100% |

第一条规则对留出的 RPC 误报 12/12，说明仅与 GET 对照会把合法流式业务也标出来。第二条规则能区分本批合成实现，说明扩充对照后 N1 仍有固定特征。留出 N1 只有 12 条；这是单设备、单网络、同一 TLS 栈的合成实验，**不是 GFW 识别率、抗封锁概率或真实网站大样本评估**。同批 ClientHello 归一化特征一致，不能推导与浏览器一致。

抓包校验：72 个 ClientHello 与顺序样本一一对应，均有 SYN，双向重组连续，服务端 TLS 无未解析尾部。N1/RPC 各 24 条均无 RST。GET 有 51 个 RST 包（不是 51 条失败请求，可能含重复），虽然 24 条载荷与终止读检查成功，其关闭行为与另两组不同，属于对照局限，不能把这一差异包装为 N1 的隐蔽优势。Go TLS 的 EOF 观察也不能独立证明收到对端 close_notify。

## 下一步改动的验收门槛

1. 用隔离发送事件与记录长度定位 N1 多出的客户端记录来自请求头、载荷、FIN、HTTP 终止块还是 TLS 关闭；先证据后调整。
2. 尝试合并同一写入批次中已经可用的数据和边界，避免人为定时等待，不移除 FIN、不省略 EOF 校验、不关闭证书验证。
3. 修正普通 GET 对照的关闭差异，再用新的尺寸、请求序列和独立样本验收；本次留出数据已经看过，不能再称为后续独立验证集。
4. 若仅靠记录计数仍能稳定区分，再研究真实业务分布和适量填充。当前没有依据采用全量随机填充，也不能承诺新协议无法识别。

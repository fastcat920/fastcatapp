# N1 第六阶段：上行匹配对照与下行小记录定位

日期：2026-11-24。安卓荣耀 TFY-AN00，原生独立测试程序；同一 Wi-Fi → zlhk.fastcat.ink:18461/TCP → 回环合成源。不是正式 App/VPN 或真实 GFW 识别测试。

## 完成情况

24 对、48/48 新连接通过逐字节载荷、消息结束、HTTP EOF 和 TLS 终止读检查。每对上行三次明文写入长度、完整客户端 TLS 记录类型/长度序列、唯一 TCP 载荷字节数均相等。选定的上行特征无法在这些成对样本中提供区分能力，但双向小记录计数仍有差异。

已逐次对齐服务端发送事件和完整 TLS 记录。N1 数据阶段的 24 条小加密记录中：**15 条是大写入超过 16 KiB 后产生的 TLS 短尾，9 条是目标 HTTP 流的剩余小 DATA**。正常 RPC 也有 **10 条 TLS 拆分短尾**。没有直接修改 N1 线格式、填充或第五阶段合并策略。

## 匹配对照怎么构造

普通合成流式任务 `/j` 使用 JSON 命令开始输出，客户端读完输出后发送数字 0 作为完成回执。不使用 N1 记录、exporter、认证或目标转发。

两条链路都遵循：立即响应确认头 → 客户端发送业务命令 → 服务端输出 → 客户端验证输出结束 → 发送 FIN/完成回执和 HTTP 上传结束 → TLS 关闭。

控制的 JSON 命令和回执用合法空白补齐到已观察的 N1 帧体长度，头部使用有界应用元数据补齐。三个完整上行写入长度逐项相同，实际公网客户端 TLS 记录序列与总字节数也逐对相同。控制没有复制 N1 帧内容或验证逻辑。

这是**有意构造的匹配对照**，不能证明真实网站普遍采用这种流量。精确壁钟时序、认证语义、下行应用格式和 TCP 分段没有被强制匹配。N1 要携带目标 HTTP 响应头，RPC 输出原始数据，两者下行仍不同；N1 的 TCP 读取也可合并源的分块。

## 采样方案

在采集前冻结 PHASE6-PLAN.md 和训练/留出方案。训练输出尺寸 2048/20480/81920 B，留出 4096/40960/163840 B，未复用前两轮公网留出尺寸。每个尺寸分别突发 16 KiB 和分段 4 KiB/12 ms，两次重复。训练与留出各 12 对。小于一块的样本不发生主动间隔。

每对必须先跑 N1 才知道实际随机填充后的长度，因此对内始终 N1 在前，只有对的顺序随机化；**本轮不用于宣称速度优劣**。公开抓包前的 8 KiB 试跑单独保留在 pilot.json，未进入 48 条结果。

## 小记录来源：与 TLS 记录逐项核对

“小记录”定义为外层加密 TLS 记录长度 <=256 B。表中每种方式各 24 条连接：

| 来源 | N1 | 普通流式任务 |
| --- | ---: | ---: |
| 受保护握手小记录 | 72 | 72 |
| HTTP 确认响应头 | 24 | 24 |
| N1 FIN / HTTP 输出结束块 | 24 | 24 |
| TLS 关闭小记录 | 24 | 24 |
| 数据阶段的小记录 | 24 | 10 |
| 合计 | **168** | **154** |

握手和关闭分类仅针对本次 Go TLS 1.3 实现：前四条受保护握手记录中有三条小记录，末尾关闭记录为 19 B。它们不是 N1 业务消息，不能把全部小记录归因于代理封装。

服务端明文写入与加密记录按顺序完整对齐，TLS 1.3 内部类型与 AEAD 标签合计 17 B；所有写入字节都被消耗且没有未归属应用记录。该定位没有解密或导出 TLS 密钥，不是通用的互联网流量解密/识别工具。

### 1. 超过 TLS 单记录上限的短尾

N1 载荷最多 16384 B，再加 N1 记录头、随机填充和 HTTP chunk 边界，整个 Write 可达 16431 B。TLS 的最大明文记录为 16384 B，较大写入会被拆分。

实测 N1 示例：16411 B 明文写入 → 16401 B 和 44 B 两条加密记录；后者只承载 27 B 剩余明文。N1 数据阶段共出现 15 条这种短尾。

正常 RPC 同样受影响：16384 B 数据加 8 B HTTP chunk 边界成为 16392 B，实测拆成 16401 B + 25 B；本轮出现 10 条。可见这类短尾并非 N1 独有。TLS 早期的自适应记录大小也会影响拆分，不能假设所有大 Write 都恰好产生相同数量的小尾记录。

### 2. 内层 HTTP 总长度偏移后的剩余 DATA

另外 9 条 N1 小记录本身就是小 DATA 写入，未发生大写入拆分。它们的载荷分别为 137–139 B，逐条等于该目标响应的 HTTP 头总字节数（所有 DATA 载荷总和减去已知正文长度）。正文尺寸恰为块大小的整数倍，附加 HTTP 响应头使整个透明流出现同量的末尾余数。

**这不表示 HTTP 头被发送到了末尾**：响应头仍在开头，末尾是剩下的正文。此次 24 个含目标响应前缀的首 DATA 写入均携带了更多数据，没有单独形成小记录。此前“可能是单独目标响应头”的假设在本轮没有得到支持。

这个余数与测试源采用的 HTTP 响应格式和整块正文尺寸有关，不能直接推广到所有 HTTPS、游戏或任意 TCP 业务。透明转发必须保留目标字节，不能通过删除 HTTP 头解决。

## 新留出样本的判别结果

预定单层阈值模型仅用训练数据选取规则。每项留出集含 12 条 N1、12 条 RPC。TP/TN/FP/FN 为命中 N1、正确排除 RPC、误报 RPC、漏报 N1。

| 特征范围 | 训练选中的规则 | 留出 TP/TN/FP/FN | 平衡准确率 |
| --- | --- | --- | ---: |
| 仅上行特征 | client_records > 4.0000 | 12/0/12/0 | 50.0% |
| 双向记录计数 | server_small_records > 6.5000 | 7/10/2/5 | 70.8% |
| 计数 + 双向字节量 | log_server_tcp_bytes > 8.8860 | 12/0/12/0 | 50.0% |

上行特征在每一对中实际相同，所以仅上行规则得分 50%，是这份构造对照的预期验证，不能解释成真实网络上行不可识别。双向计数规则仍有区分信息，但存在 2 次 RPC 误报和 5 次 N1 漏报。

完整特征模型没有优于计数模型：它在训练中选了下行字节数规则，留出时对全部 RPC 误报，得分 50%。两条候选训练成绩均约 66.7%，固定实现按浮点比较选择了字节量规则；**不能把该模型的失败解读为更多特征没有信息或更强分类器也无法识别**。本轮留出结果未用于重选阈值或优化发送参数。

这些结果是单网络、同 TLS 栈、合成源的有限实验；不是 GFW 的识别率、封锁概率或现实流量总体的误报率。

## 自检与恢复

Mac race 测试、vet、安卓 Matched/Coalesced/ClientEmission 回环检查通过；48 个抓包握手与样本顺序匹配，均有 SYN、双向重组连续、双向 TLS 无未解析尾部，所有样本均无 TCP RST。服务端此次调用日志中 panic、transport failure、transport error 均为 0。

服务端只在本轮临时开启 workload-controls + trace-writes，日志只存帧类别和长度，不记录 Cookie、目标、内容、IP 或 TLS 密钥。采集后移除 phase6-controls.conf，已恢复原二进制，SHA256 为 `0e5ed17e6e94ac775d8d52b0a65f26e5db57fd2c1efd57ab0144d7b8707c2d8e`。原始抓包仅保存在服务器私有目录 `/opt/fastcat-n1-lab/phase6.pcap`，权限 600，SHA256 `5c53c20cdde52c0f1f9f4a2b1fc18a13ca983c8e82d87b3818754a4a751c90f0`；同一解析器在服务器生成匿名元数据取回，未下载原始内容。

正式 APK、面板、443、节点 93/94 未修改，原服务均 active。恢复后的新客户端再次校验成功，公共 `/j` 恢复 404，正式 HTTPS 返回 200；安卓临时测试二进制已删除。未推送 GitHub。

## 下一步建议

优先试验“把封装后的完整 Write 控制在 TLS 最大明文记录内”，而非先增加随机填充。例如在最坏 31 B 填充下，N1 DATA 载荷上限候选为 16337 B，使 N1 头、填充和 HTTP chunk 合计最多 16384 B。它只是下一轮候选，**本轮未实施**；早期 TLS 自适应拆分和任意目标短尾仍然可能存在，不能保证消除全部小记录。

需要在新的非整块正文尺寸、上行匹配的控制和新的留出样本上验证，并同时测记录数、字节开销、首包与吞吐。不要为了消除 137–139 B 的测试源余数而删除目标内容、等待更多业务数据或大量补齐。

# 并行确认轻量版：最终对照

## 交付

新增实验模式IndependentPipelined（light-fast）。保留旧light和sealed，不自动切换。
旧light等CLIENT_CONFIRM后的READY才发OPEN；新模式从认证过的SERVER_ACCEPT取得session_id，
提交CLIENT_CONFIRM后即可发送独立OPEN。服务端先验证证明并保留唯一counter，确认门通过
后才执行目标DNS/拨号。确认失败、取消、过期或确认门缺失均失败关闭，不转发业务数据。

新模式去掉一次READY响应依赖，而不是跳过CLIENT_CONFIRM。仅对首个冷业务有结构收益；
已认证连接上的业务原本不需要完整Noise握手，不能期待同样的热连接提速。

安全复核后最终格式使用FCI2加密目标和认证OPEN_RESULT：目标使用会话派生ChaCha20-Poly1305
及counter nonce；成功/失败回执使用独立派生HMAC密钥绑定完整请求、TLS binding和状态。
客户端验证回执后才返回业务连接。后续数据仍是轻量TLS保护，不是全程内层AEAD。
这保留了并行期间的目标保密以及发送业务数据之前的密钥/通道确认。长度未隐藏。
前一次未补强的试跑不作为最终对照，最终数据仅来自上述FCI2版本。

另修复拒绝/错误路径的H2关闭顺序：先取消请求和关闭pipe，再关闭响应体，避免等待请求
deadline。成功业务路径没有重试或重放。所有模式沿用此前缓冲复用和H2响应头合并。

## 自检

- 原v3、旧light及sealed回归继续通过。
- 新模式H2/H3八路大数据、慢流隔离、半关闭、取消、认证丢失和私网拒绝通过。
- 端到端刻意让有效OPEN先于确认到达，确认前无目标连接；确认成功后只拨一次。
- 完整无效AEAD确认标签导致排队请求失败；确认前重复counter也拒绝。
- 缺失确认门、取消与确认竞争均失败关闭。
- Python cryptography参考向量核对FCI2密文、回执和模式域分离；篡改密文/绑定以及
  伪造OPEN成功回执都被拒绝。
- Go1.26.2完整race重复2遍、额外新模式重复测试、vet通过；Go1.27.3新模式及相关race通过。

## 最终安卓对照条件

当前连接荣耀安卓独立核心程序，前后默认Wi-Fi均为network 171。目标example.com:443，
HTTPS HEAD验证200。香港同一服务器v2 19442、两种light 19443；同一域名证书、固定IP，
无ECH/入口DoH，详细诊断日志关闭。两服务端Go1.27.3，一个安卓Go1.26.2对照程序。

三版本和H2/H3先后轮换。每个版本/承载冷启动20次；复用20次，使用3个独立会话轮换，
样本7/7/6；并发5批×4条，同批同会话，三池批次2/2/1。每条业务仍新建目标TLS。
正式360/360成功：v2、旧light、新light各120/120；另18次预热成功，不计入正式分位数。
失败不重试替换。P95采用成功样本最近秩分位数。三池用于减少单连接影响，不是App自动池实现。

| H3冷启动 |595 / 1301|896 / 1716|735 / 1257|

相对旧light，新模式冷启动中位数H2减少114ms，H3减少161ms，与减少READY等待的方向一致。
相对v2，冷启动中位数仍高；本轮P95略好，但20个样本不足以建立稳定尾延迟优势。
热连接结果未全面改善，尤其新模式H2复用/并发慢于旧版和v2。不同会话/网络状态仍可能
影响整组；不能将所有差异归于加密、认证或发送策略。

client_ready_us含义也不同：旧light包含READY，新模式止于确认提交；不能将其直接当作
相同的服务端认证完成时刻。entry_us累计至认证门、目标OPEN和回执验证完成，首字节统计
包含完整建立过程，三组比较没有省略新模式的服务端确认等待。

## 判断

已实现并验证安全时序下的认证关键路径缩短，本轮冷启动较旧light有收益，但未全面超过v2。
生产继续保留v2。后续重点是用更多独立连接核对热路径，再拆分网络、流排队与目标TLS；
不建议直接依据一轮结果调整默认协议。隐蔽性、能耗、吞吐及长期故障恢复没有在本轮证明。

当前仅独立TCP原型，未接入正式App/面板、UDP、自动选路或DoH/ECH。手机原VPN已恢复，
临时服务和凭证清理完毕，生产443/18447未修改。
